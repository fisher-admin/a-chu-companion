# Claude 优化版本审核评价

审核日期：2026-10-08。项目：A畜伴侣。

**结论：局部优化有价值，整体升级未达到交付条件。** 新增的有序流式翻译、故障降级、取消处理和错误提示值得保留；但本次从旧 main 开发，没有纳入已完成的 build78，导致三端支持等核心能力缺失。新管线也存在已复现的段落等待、结构切分和滚动问题。建议以 build78 为整合基础，选择性迁入本次改进，而不是直接用 1.2.0 覆盖原功能。

本轮只审查和测试，未改动程序源码、切换分支、重新安装或向真实 Claude/Gemini 发送消息。新增此报告及忽略目录中的本机审核夹具、日志。

## 二、值得肯定的部分

1. **原文可以先显示，译文逐步更新。** 新管线按顺序显示并行翻译结果，取消或原文改写后，旧结果不能覆盖新内容。对应 `Sources/StreamTranslationPipeline.swift:74`、`Sources/ReplyMonitor.swift:272`。
2. **翻译失败后的处理更清楚。** 限流、超时、密钥错误可以逐段转用系统翻译；连续失败暂时停用 AI，并遵守服务器给出的等待时间。取消操作不会被误认为应继续降级。对应 `Sources/FailoverTranslator.swift:57`、`Sources/AICircuit.swift`。
3. **围栏代码在回复管线中原样保留。** 本轮真实系统翻译测试已经验证固定代码块未被翻译。
4. **持续无法识别页面时给出提示并继续尝试。** 45 秒结构错误提示比无声等待好，但它不能代替对不同页面结构的适配。
5. **测试不是完全空白。** 本轮重新执行的离线测试、本机 HTTP 测试、真实苹果翻译与完整源码编译均通过。Claude 也明确把真实 Claude/Gemini 和最终夹具界面列为未验收项。

## 三、需要优先处理的问题

P1 表示应在替换正式版本前处理；P2 表示影响体验、可靠性或发布完整性。

### P1：没有保留 build78 的三端能力

当前 `Sources/ClaudeAccessibility.swift:29` 按应用名单连接，包含 Claude 桌面版和数种浏览器，没有终端适配。build78 的 `CLIDelivery.swift`、`CLIInteraction.swift`、`ManualInputDelivery.swift`、`LocalBridge.swift` 等不在当前工作树中。

因此，这一版不能作为已经支持 Claude Code CLI 的版本升级，也不符合“由用户选定输入位置，连接后保持”的三端一致要求。

额度也退回到“桌面登录”和“手填 session”两种来源：`Sources/ClaudeUsageMonitor.swift:60`、`Sources/ClaudeUsageView.swift:73`。build78 的原生网页 Usage 读取、CLI 来源及当前账户识别没有纳入。已保存的其他来源值在此版会落回桌面来源，见 `Sources/ClaudeUsageMonitor.swift:86`。不能把桌面额度当作当前网页或 CLI 账户的额度。

**建议：** 保留 build78 的连接、发送、三端额度和账户识别，把流式翻译作为内部改进接入，不重新定义三端行为。

### P1：网页 Code 路径与不同语言的回复识别回退

`Sources/ClaudeAccessibility.swift:130` 只接受 `/chat/`、`/new` 和首页，不接受 Code 的 `/code/...` 页面；这一检查会直接停止该页面读取。消息序号、作者与部分状态识别又只接受英文标签，见 `Sources/ClaudeAccessibility.swift:216`、`Sources/ReplyCore.swift:45`。

build78 中已有的 Code、本地化和分段识别测试也没有纳入。新加“识别失败提示”有用，但不能证明 Chat/Code 读取已恢复。

**建议：** 恢复现有 Code 和本地化适配及其测试，之后才验收新的流式管线。

### P1：重新加入用户已明确取消的译文质量门槛

`Sources/FailoverTranslator.swift:66` 对 AI 结果进行语言、长度等审核；`Sources/TranslatorModel.swift:227` 将它用于发送前的翻译。用户已经要求取消额外质量检查，翻译后直接按设置发送。

本轮用一条正常的算法名称比较句复现：中文保留 `RandomForestClassifier` 等名称，语义正确，但中文字符比例较低，被判定为 `language` 不合格，触发不必要的系统降级。这种规则会把正常技术文字当成失败，增加等待。

另外，`Sources/TargetBridge.swift:137` 又要求输入框内容和光标完全等于连接时的值；`Sources/TargetBridge.swift:187` 最多等待约 30 秒核对粘贴，无法读取文字就拒绝自动回车。这不是用户已确认的手选输入区域逻辑。

**建议：** 去掉语义、语言比例、长度比例等质量门槛。保留任务取消、目标软件关闭、连接已经失效、服务返回错误等必要的运行检查；用户明确选择的输入位置应继续作为目标。

### P1：独立 Gemini 配置、密钥隔离和升级兼容性缺失

当前设置只有“系统翻译”和通用“AI 翻译”，见 `Sources/Views.swift:264`。“使用 Gemini 地址”只是填入兼容接口地址，不能代替原有独立 Gemini 接入。

`Sources/TranslatorModel.swift:110` 读取已保存的翻译方式，但 `Sources/TranslatorModel.swift:216` 只将 `ai` 识别为远程翻译；旧的 `gemini` 选择进入系统翻译分支。Gemini 独立密钥读取也没有纳入。

当前 `Sources/Credentials.swift:5` 只使用一个通用密钥账户，发送时配合任意配置地址，见 `Sources/Core.swift:198`。原版按服务地址隔离密钥的 `TranslationProfile.swift` 已缺失，换地址后可能把原服务的密钥用于另一服务。此次审核没有读取真实密钥，也没有证据表明已经发生泄露。

**建议：** 恢复独立 Gemini、按服务隔离的密钥与非阻塞授权处理，并为旧设置增加兼容验证。系统翻译仍保持默认。

### P1：阶段性正文稳定后仍可能不及时翻译

`Sources/StreamSegmenter.swift:194` 遇到末尾空白直接等待后续文字，末尾句号也有类似等待。测试输入一段以句号和两个换行结束的完整阶段说明，重复提供 8 次相同快照，原文已经可显示，提交给翻译的段数仍为 0。

在 Code 模式暂停输出、执行较长工具任务时，下一段正文迟迟不来，前一阶段就仍然不翻译。取消“全部完成后等待 3 秒”并没有解决这个情形。

当前所有分段也合并进同一气泡，见 `Sources/ReplyMonitor.swift:302`；没有保留用户选择的“每个完成分段单独显示一条”。

**建议：** 将“稳定并有完整边界的阶段正文”及时交给翻译，不依赖下一阶段字符到达，也不等待全部任务结束；原文立即显示和及时翻译须同时成立。显示和十条记录计数应保持用户确认的分段规则。

### P1：表格与代码结构不能完整保留

当前缺少 build78 的 `MarkdownTable.swift`、`TranslationStructure.swift`、`SystemTranslationProtection.swift`。`Sources/MessageText.swift:22` 使用普通文字显示，原来的表格专用布局没有纳入。

新分段器在约 800 字符处切分时，没有优先保留表格行和行内代码结构，见 `Sources/StreamSegmenter.swift:168`。本轮分别使用较长表格行和较长行内代码复现，均被拆开。表格原文拼接后并未少字，但分开提交翻译的部分已经不是完整表格行；这增加格式破坏风险。

**建议：** 保留表格行、列结构、代码、链接和公式等不能任意拆分的内容，再在可翻译单元内限长。结构保护应同时适用于系统翻译和 AI 翻译，不依赖译文质量审核。

### P2：长译文更新会打断阅读

`Sources/MessageText.swift:38` 每次文字变化都滚到顶部。本轮将长回复滚到纵向位置 300，追加一个译文段落后位置变为 0。

**建议：** 首次展示新回复从头开始；同一回复继续更新时，保留用户当前阅读位置。只有用户主动选择跳到最新内容才移动。

### P2：十条记录限制只作用于界面，后台仍累积回复

`Sources/TranslatorModel.swift:65` 裁剪界面历史，但 `Sources/ReplyMonitor.swift:294` 保存的 `live` 回复和管线没有同步清理。

本轮完成 30 条模拟回复，界面只显示 10 条，后台仍保留 30 条。持续运行或切换会话会继续积累原文、译文和管线对象。

**建议：** 同时裁剪已结束任务和界面记录，保留正在处理的任务以及确有需要的重试对象；清除历史应清除对应缓存。

### P2：额度更新依赖翻译完成，超限回复不会刷新

真正触发额度更新的位置是译文完成回调，见 `Sources/ReplyMonitor.swift:303`。超过上限的回复在 `Sources/ReplyMonitor.swift:281` 提前退出。

本轮读取 50,001 字符的完整原文，原文被保留，但额度刷新计数为 0。`Tests/ModelTests.swift:53` 直接调用通知方法，无法发现真实读取流程没有发通知。

**建议：** 以获取到新的正式回复版本作为额度更新触发条件，与是否成功翻译、是否超限分开。

### P2：发送成功的判断比文档声称的宽松

`Sources/TargetBridge.swift:199` 注释声称输入框清空才证明发送，但 `Sources/Core.swift:56` 实际接受“剩余文字不包含原译文”。本轮给出非空 `Loading...`，返回“已发送”。

这不能证明真实 Claude 收到了消息，尤其页面重建或显示其他内容时容易误报。

**建议：** 将“已经填入”“已经按发送键”“已获得提交结果”分别表达，避免仅凭文字变化宣称服务已接收；不要再因此引入语义质量审批。

### P2：发布检查与记录还不完整

1. `.gitignore` 没有保留 build78 的 `.omx/`、`output/` 等本机产物排除规则，当前它们变为未跟踪文件。它们并不因此已经上传，但不能随意批量加入提交。
2. 本轮 `python3 Tools/check_repository.py --history` 失败；历史告警中的 4 个 token 全部是同一固定虚构 session，原版对应白名单遗漏，而不是本轮发现真实登录信息。仍应修复检查工具，让发布检查实际通过。
3. Google API key 的检测规则也没有保留。
4. 当前 GitHub CI 使用相同的历史检查命令，即使远端没有本机 `.omx` 文件，也仍会遇到上述历史虚构数据告警。
5. 更新记录没有纳入 build30 至 build78 的功能变化，应用构建编号回到 29；Git 历史仍在，但发布记录不能用新版本号掩盖遗漏。

**建议：** 恢复仓库保护规则与历史记录；分别记录当前工作树检查、完整历史检查、模拟测试和真实测试，不能把它们合并为“全部通过”。

## 五、建议的整合顺序

1. **先恢复正确基础和既定需求。** 以 build78 为基础保留三端、账户、额度、Gemini、表格及历史记录；明确禁止重新加入质量审批、浏览器额外组件依赖或自动推翻用户指定的输入位置。
2. **再迁入经过验证的新改进。** 迁入流式有序管线、取消和改写隔离、故障降级与结构错误提示；解决稳定末段、长表格、长代码、滚动和缓存裁剪。保留必要的运行错误检查。
3. **最后按完整产品范围验收。** 同时运行 build78 的回归和新增测试，再进行桌面 Chat/Code、网页 Chat/Code、不同终端中的 CLI 测试；逐项验收翻译、填入、回车、自动读取、历史、额度来源、换账户及重启记忆。真实 Gemini 单独验收。

上述整合尚未实施。本轮交付为审查报告和验证结果，当前程序源码与安装保持原状。

## 六、正式发布整理说明

此报告记录 build29 的审核快照。用户随后明确指定将 1.2.0 正式发布；发布整理使用 build79，恢复本机产物忽略规则和凭据检查规则，公开保留本报告及已知问题。上述产品功能问题没有在发布整理中修复，不能把新的构建号理解为三端能力已经恢复。
