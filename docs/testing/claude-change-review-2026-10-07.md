## 结论

**这次修改有实质收益，但尚不满足可发布、三端完整验收通过的标准。**

Claude 增加了共享译文检查、系统翻译兜底、按完整回复刷新额度、Code 流式容器的连续识别，以及 67 项新检查。对旧版“大段附加答案”的保护有所改善，系统兜底的发送方向也保留了人工检查步骤。

独立复跑现有完整模拟回归全部通过，但新增兜底绕过限流、全局术语替换改坏正常译文、等待连接时旧来源报告恢复显示等缺口没有被现有测试覆盖。短小附加答案、否定含义反转仍可通过新检查；不能把它称为已经解决“翻译服务只做翻译”。

本次没有修改产品源码、安装或重启伴侣、改变登录信息、发送真实 Claude 消息，或调用真实 Gemini。新增内容只有独立审查报告和忽略目录中的验证副本、复现用例及日志。

## 发现及修复建议

### R1 — 高：系统兜底吞掉原服务的限流要求

依据：[ReplyPipeline.swift](../../Sources/ReplyPipeline.swift#L151)，尤其第 155–160 行及第 175–178 行。

新增捕获会把所有非取消错误交给系统翻译，包含 `ServiceCooldown`。系统翻译成功后，外层记录等待时间的分支没有执行。下一个片段立即再次请求原服务；系统翻译也失败时，原来的限流错误被局部失败覆盖，等待后也不再自动恢复。

独立复现：两个完成分段；原服务每次返回等待 60 秒，系统兜底成功。模拟时钟始终为 100，原服务仍被调用两次。相同管线去掉兜底后只调用一次，正确等待。兜底也失败的用例中，时钟推进到 161，原服务仍未自动重试。

**建议**：先按错误类型记录原服务冷却时间；冷却期间可继续系统翻译，但不得每段重新试云端。兜底失败保留两种错误及恢复条件。503、超时、限流、鉴权、取消分别处理，取消不转服务。增加多分段限流及兜底失败的回归。

### R2 — 高：等待连接状态不能阻止旧额度报告恢复显示

依据：[ClaudeUsageMonitor.swift](../../Sources/ClaudeUsageMonitor.swift#L144) 和第 318–336 行。

`awaitChatEntrance` 清空显示并设为等待，但保留旧绑定；`receive` 发布额度时没有检查等待状态。旧 CLI/Web 报告仍可能填回主界面。这不等于混用了另一个账户凭据，而是旧入口没有经过本次聊天连接确认就恢复显示。

独立复现：连接合成 CLI 来源，收到额度；进入等待状态后，继续收到同绑定的新报告，`awaitingEntrance` 仍为真，额度却已显示。另有从已保存绑定启动、未连接聊天即收到报告的复现。

**建议**：保存的偏好与本次运行的有效连接分开。等待时可收集候选，但不得发布主界面额度；只有当前入口、绑定和账户均有效时才发布。切换来源和等待连接时一并撤销旧的延迟刷新；迟到任务须核对连接代次。

### R3 — 高：为一个研究问题定制的术语纠正污染其他译文

依据：[SystemTranslationProtection.swift](../../Sources/SystemTranslationProtection.swift#L19)，尤其第 22、26、31–32 行。

只要英文片段出现一个词，就在整个中文结果中替换对应短语，没有判断该词所在领域或对应位置。

独立复现：

| 原文 | 本来可用的译文 | 替换后 |
| --- | --- | --- |
| `The finding was due to chance.` | 这个发现是偶然的。 | 这个发现是随机水平。 |
| `The judge was unbiased.` | 这位法官不偏不倚。 | 这位法官无偏。 |

`engine` 也会使机械场景的“发动机”全部变为“引擎”。这一例未必必然错误，但进一步说明规则没有领域边界。不能把“偶然”统一当成模型预测的随机水平，也不能把所有“公正”都当成统计无偏性。

**建议**：移除这些宽泛强制替换。确需学术术语表时，以用户选择的领域或明确上下文限定；保留否定、修饰语及实体，不能仅因某个英文词出现就全句替换。用统计、日常、法律、机械和软件界面的交叉样本验证。

### R4 — 高：新检查只能拦部分形状，仍不能保证只翻译

依据：build63 历史源码 `TranslationFidelity.swift` 第 74 行（提交 `207a06d`）、[TextTranslation.swift](../../Sources/TextTranslation.swift#L68)。

长度、新增结构和末尾问号的检查有价值，但短句的固定余量允许附加回答；没有验证语义、否定或目标语言。表格单元格有上下文时，还会绕过新共享检查。

独立复现，以下结果均被接受：

- `请保留原有设置。` → `Please retain the existing settings. They are already optimal.`：增加评价。
- `不要删除文件。` → `Delete the files.`：含义相反。
- 有表格上下文时，`是否可行？` → `Yes, it is feasible.`：回答了问题。

这属于原问题没有彻底解决；前两个不是此次才出现的语义错误。代码注释及原草案也承认长度规则不能证明忠实，应保留这一说明。

**建议**：统一正文与单元格的基础校验，并在拼接完成、发送前再检查整条结果。增加短指令、否定、不确定性、数字、实体、引用命令和四种目标语言的双向样本。明显冲突或疑似补充内容不得自动发送，保留中文草稿和候选译文。结构化输出可限制响应格式，但不能保证含义；应单独核验接口支持，不能视为语义修复。暂不建议为每个片段固定再调用一个模型审核，以免免费额度与等待时间显著增加。

### R5 — 中：负数被当成新增列表，合法译文遭拒

依据：build63 历史源码 `TranslationFidelity.swift` 第 60 行（提交 `207a06d`）。

列表识别允许列表符号后没有空格，因此 `-0.3` 被识别为列表。独立复现：`负零点三` → `-0.3` 因“原文没有的列表”被拒。系统兜底也使用相同规则，未必能救回。

**建议**：按真实列表边界判断，区分负数、公式、连字符与项目符号。补充负小数、负指数、带符号区间，以及中文项目符号的对照用例。

### R6 — 中：草案承诺的持续读取恢复尚未实现

依据：[ReplyMonitor.swift](../../Sources/ReplyMonitor.swift#L215) 和审计草案 §4.2。

普通读取错误累计五次仍会永久暂停。独立用例确认 `watching` 变为假；随后窗口恢复不会自行开始读取。这是原有缺口，并非新回归；不能因为新增流式容器连续识别就认为所有读取中断已解决。

**建议**：短暂辅助功能不可访问采用有上限的逐步退避，成功后恢复正常轮询；保留目标身份及已有记录。用户停止、权限撤销、应用退出等情况另行处理，不无限忙等。验证后台切换、暂时隐藏、睡眠恢复、长任务和明确停止。

### R7 — 中：按文本内容过滤界面提示会误删正式回复

依据：[ReplyCore.swift](../../Sources/ReplyCore.swift#L302) 和第 423–426 行。

新增过滤删除任何与反馈提问完全相同的静态文本，而不是限定为反馈控件。独立复现：正式 assistant 消息的正文恰为 `How is Claude doing this session?` 时，解码结果为空。正常的引用、示例或翻译任务也可能包含这个句子。

**建议**：依靠控件所在区域、角色和作者边界排除反馈组件；正式正文中的同名文本必须保留。正在运行的工具过滤也补充“正文讲解 running 状态”的反例。句内合并继续保留真实换行、表格、代码和工具边界，不仅靠标点或大小写猜段落。

### R8 — 中：切换会话后，相同回复会漏掉额度刷新

依据：[ReplyMonitor.swift](../../Sources/ReplyMonitor.swift#L116)。

去重只比较序号、分段号、正文，不包含会话。两个会话都在消息 2 完成相同回答时，只触发一次完成回调。独立复现完成回调为 1，应为 2。

**建议**：以会话、轮次和完成状态为键去重。同一会话重复轮询只刷一次；不同会话的相同正文分别刷新。延迟刷新同时核对当前来源和连接代次，避免旧会话的任务作用到新来源。

### R9 — 中：公开仓库检查未通过，版本记录也未完成

依据：[FidelityFallbackTests.swift](../../Tests/FidelityFallbackTests.swift#L9)、[check_repository.py](../../Tools/check_repository.py#L23)、[审计草案](audit-plan-2026-10-07.md)、README 和 CHANGELOG。

新增测试沿用另一测试文件的合成 session 值，但检查器只在原文件中精确放行，因此工作树和可达历史对象都命中。已核实该字符串是测试夹具，不是从你的钥匙串读取的个人 session；本次没有发现其他凭据模式命中。模式扫描本身不能证明不存在任何其他形式的秘密。

当前程序已安装 build63，但 README 仍标记 build58，草案仍声称工作区干净、尚未修改源码，CHANGELOG 未补齐本轮 build59–63 的变化。没有找到与本轮修改相对应、区分三端完整实测与局部探针的最终验收报告。

**建议**：精确登记已核实的假凭据或采用不会冒充真实凭据格式的夹具；不要放宽整类 session 检测，也不要改写历史掩盖命中。补齐本轮版本记录及最终测试报告，明确每个构建实际修改、安装和验证的范围。保留已有历史；提交前重新跑公开文件及历史检查。

## 辅助函数层面的保留意见

`SystemTranslationProtection.translate` 在恢复占位符以后做繁简转换，直接调用时会将已恢复的 `繁體.md` 改成 `繁体.md`。独立辅助函数用例已复现。不过普通文件名在当前主翻译链中通常已由外层 `TranslationStructure` 先剥离保护，因此**不据此认定普通文件名已在当前产品界面损坏**。

建议在占位符未恢复时转换正文，最后恢复字面量；无需为了简繁字形重复调用翻译。补充中文路径、文件名、引号内专名及标识符的端到端验证。

此外，发送方向的远程错误捕获范围包含 `finish` 中的回填错误（TranslatorModel 第 327–329 行）。源码上可见：焦点变化导致的回填失败也可能被提示为 Gemini 翻译失败并重新系统翻译。本次未做真实回填来复现此分支，故将其列为待验证项。建议将翻译异常与回填异常分别处理；回填失败保留已生成译文，不能重新翻译后掩盖失败原因。

## 建议的实施顺序与完成条件

### 第一批：先消除新回归

1. 修复原服务冷却被系统兜底吞掉、等待连接仍发布旧额度报告。
2. 移除没有领域限制的术语强制替换。
3. 修正负数误判及正文提示误删；完成回调加入会话身份。

完成条件：上述独立反例先作为产品失败用例，再逐项转为通过；同时保持原有正文即时显示、阶段性翻译、表格和代码保护、后台读取、取消与迟到结果隔离。

### 第二批：补齐恢复与翻译质量

1. 正文与表格共用基础校验，整条发送前增加检查；明确启发式规则的边界。
2. 读取短暂失败自动恢复，远程失败分类、退避和重试有预算。
3. 设置、来源、会话切换时统一撤销过期任务；不抹去已有中文和中文草稿。
4. 简繁转换只作用于译文正文，字面量最后恢复；统一各翻译方式的规则来源。

完成条件：合成流式回放证明稳定段先于任务结束显示中文；429 不越过等待时间；503 与系统兜底均失败时可以恢复；没有重复发送、跨来源额度覆盖、表格数值或代码变更。

### 第三批：一次冻结、完整复测、再真实验收

先完成源码、模拟测试和仓库检查，冻结一份最终候选；最后一次安装，沿原签名身份保留旧构建。避免每修一项就升级和要求重新连接。
